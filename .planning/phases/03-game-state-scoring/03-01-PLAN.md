    **Step 2: Add temporal middleware to showStore**

    Wrap the store creator with zundo's `temporal` middleware. The middleware ordering MUST be: `broadcast(persist(temporal(creator)))` — temporal wraps the creator innermost so it captures state changes before persist and broadcast. This ensures:
    - temporal tracks the raw state mutations
    - persist saves the current state to localStorage
    - broadcast sends post-persist state to other windows

    Import `temporal` from `'zundo'`. Configure temporal with:
    - `limit: 50` — keep last 50 states to prevent unbounded memory growth
    - `partialize` — only track score-related fields: `rightScore`, `leftScore`, `rightsTurn`, `turned`, `sidesSwapped`
    - This means undo/redo only affects scoring state, not data, quickQuestion, etc.

    **Step 3: Add swapSides action to ShowState interface and implementation**

    Add to ShowState interface:
    ```typescript
    sidesSwapped: boolean  // tracks whether sides have been swapped from initial
    swapSides: () => void
    ```

    Add `sidesSwapped: false` to initialState.

    Implementation of swapSides:
    ```typescript
    swapSides: () => set((state) => {
      if (!state.data) return state
      return {
        rightScore: state.leftScore,
        leftScore: state.rightScore,
        rightsTurn: !state.rightsTurn,
        sidesSwapped: !state.sidesSwapped,
        data: {
          ...state.data,
          leftTeamName: state.data.rightTeamName,
          rightTeamName: state.data.leftTeamName,
        },
      }
    }),
    ```
    This atomically swaps scores, team names, turn, and toggling sidesSwapped — per user decision that side swap is instant with no animation.

    **Step 4: Export temporal store access from index.ts**

    Add to `src/state/index.ts`:
    ```typescript
    export { useShowStore } from './showStore'
    export type { EpisodeData, ShowState } from './showStore'
    ```
    The temporal store access (`useShowStore.temporal`) is accessed directly from showStore in hooks — no separate export needed, but ensure showStore exports are correct.

    **IMPORTANT middleware ordering note:** The existing pattern is `broadcast(persist(creator))`. With temporal added, it becomes `broadcast(persist(temporal(creator, options)))`. The temporal middleware must be innermost because:
    1. It needs to intercept `set` calls before persist processes them
    2. The broadcast middleware should send the final persisted state, not intermediate temporal states
    3. This prevents the pitfall where BroadcastChannel echoes undo actions (Pitfall 7 from research)
